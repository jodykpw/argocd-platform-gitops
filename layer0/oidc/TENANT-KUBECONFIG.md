# kubectl for tenant users (zeedlogic, jodywan)

- Tenant users use `kubectl` through **Capsule Proxy**, not directly against the API server.
- The proxy shows each user only their own namespaces and the cluster-scoped items their tenant may use.
- What each role may do: `docs/tenant-access-model.md`.

| Item | Value |
|---|---|
| Server | `https://10.1.5.171:9001` (Capsule Proxy, MetalLB address; the Mac or laptop needs a LAN or VPN route) |
| Certificate | Self-signed, generated by the proxy chart. The public certificate is `proxy-ca.crt` (ask the platform team, or see "Get the certificate") |
| Login | Authentik (OIDC) through `kubectl oidc-login` (install with `brew install kubelogin`) |
| Issuer | `https://authentik.jodywan.com/application/o/kube-apiserver-oauth-app/` |
| Client ID | `BJf5svepOPOag0dbh48rzIvGOhg6I9UagQ0QxQjJ` (the Authentik provider is a **Confidential** client: if the login fails with `invalid_client`, ask the platform team for the client secret and add `--exec-arg=--oidc-client-secret=<secret>` to `set-credentials`; never commit it) |
| Test users | zeedlogic: `owner@zeedlogic.com`, `dev@zeedlogic.com`, `viewer@zeedlogic.com`. jodywan: `owner@jodywan.dev`, `dev@jodywan.dev`, `viewer@jodywan.dev` |
| Your groups | `zeedlogic-owners|developers|viewers` or `jodywan-owners|developers|viewers`, set in Authentik by the platform team |

## Set up (once)

```bash
# 1. The proxy certificate (public) saved as ~/proxy-ca.crt, then:
kubectl config set-cluster k8s-1-proxy --server=https://10.1.5.171:9001 \
  --certificate-authority=$HOME/proxy-ca.crt --embed-certs=true

kubectl config set-credentials oidc --exec-api-version=client.authentication.k8s.io/v1 \
  --exec-interactive-mode=IfAvailable --exec-command=kubectl \
  --exec-arg=oidc-login --exec-arg=get-token \
  --exec-arg=--oidc-issuer-url=https://authentik.jodywan.com/application/o/kube-apiserver-oauth-app/ \
  --exec-arg=--oidc-client-id=BJf5svepOPOag0dbh48rzIvGOhg6I9UagQ0QxQjJ \
  --exec-arg=--oidc-extra-scope=profile --exec-arg=--oidc-extra-scope=email --exec-arg=--oidc-extra-scope=groups

kubectl config set-context k8s-1-proxy --cluster=k8s-1-proxy --user=oidc
kubectl config use-context k8s-1-proxy
```

## Check it works

```bash
kubectl auth whoami          # your email and your oidc:<team>-<role> group
kubectl get ns               # only your own three namespaces
kubectl get pods -n <team>-dev
```

What you can do depends on your role:

| Role | dev, stg and prod |
|---|---|
| owner | `admin`, can create namespaces within the quota |
| developer | `edit` (deploy, exec, logs, Secrets); no Roles or RoleBindings |
| viewer | read only (`view`), no Secrets |

## Get the certificate (platform team)

The proxy certificate is public. After the proxy is installed:

```bash
kubectl get secret -n capsule-system capsule-proxy -o jsonpath='{.data.tls\.crt}' | base64 -d > proxy-ca.crt
```

Check its expiry with `openssl x509 -in proxy-ca.crt -noout -enddate`. When it is renewed, users need the new file.

## Notes

- Outside the LAN you need a VPN, or the platform team publishes the proxy on a hostname. Use that hostname as the `--server` and the certificate they give you. The API server is not reachable from outside.
- Do not use `--insecure-skip-tls-verify`.
- If `kubectl` times out, check the LAN or VPN route to `10.1.5.171`.
- If `get ns` still says Forbidden, you are probably still on the direct API server context. Run `kubectl config use-context k8s-1-proxy`.
- Platform admins keep using the API server directly (`https://10.1.5.151:6443`), not the proxy.
